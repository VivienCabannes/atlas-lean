    Paxos consensus

    Lamport's single-decree Paxos ("the synod algorithm"), the consensus core of his state-machine approach to fault tolerance. Proposers issue numbered proposals, acceptors accept them, and a value is chosen once a quorum has accepted one proposal with that value. These pages prove the safety requirements: at most one value is chosen, and only a proposed value is chosen. Liveness is not claimed; by the FLP theorem no deterministic asynchronous protocol can guarantee it in the presence of a crash.

    Model (Paxos Made Simple, Section 2.1, "the customary asynchronous, non-Byzantine model"):

    • Synchrony: none. Actions of all agents interleave in any order; there are no clocks and no timeouts.
    • Failures: agents may stop and restart; acceptors keep their promises and acceptances across restarts (stable storage); proposers may forget everything. No Byzantine behaviour.
    • Messages: sent messages persist in sets and may be used any number of times or never, so they may be delayed without bound, duplicated, reordered or lost; they are never corrupted.

    Structure. The argument comes in two layers, as in Section 2.2 of the paper.

    1. Voting. Over any history of proposals and acceptances in which proposal numbers are unique, only issued proposals are accepted, and Lamport's condition P2c holds, his induction on proposal numbers proves P2b, hence that all chosen proposals share one value. Quorums are any family of pairwise intersecting acceptor sets; majorities are the instance Lamport uses.
    2. Algorithm. Phases 1 and 2 (prepare, promise, propose, accept) form a CSLib labelled transition system. An inductive invariant (acceptors' reports stay truthful because of their promises; every proposal is justified by a quorum of reports) shows that every reachable state is a voting history, so the safety theorems apply.

    Coverage. An acceptor's response to the prepare request \(n\) reports its highest-numbered acceptance with number less than \(n\), as in step 1(b) of the derivation in Section 2.2 (p. 4). The summary of Phase 1(b) on p. 5 states the response without that bound ("the highest-numbered proposal (if any) that it has accepted"); the two differ when an acceptor has accepted a proposal numbered above \(n\) without having answered a prepare request numbered \(n\) or more, which rule P1a allows. That variant is not covered: the theorems are about the algorithm of Section 2.2 with the response of step 1(b). Within it, the model allows some extra behaviour (an acceptor need not ignore a prepare request for a proposal it already accepted, and any quorum system may replace majorities). Learners (Section 2.3) and the third safety requirement, that a process learns only chosen values, are not modelled.

    StructureA Paxos voting history#✓fully proved

    Cslib.Distributed.Paxos.Voting

    A Paxos voting history, for a quorum system on acceptors and a type of values, consists of two relations: proposed b v, a proposal numbered \(b \in \mathbb{N}\) with value \(v\) was issued, and voted a b v, acceptor \(a\) accepted it. They must satisfy:

    • unique numbers: different proposals have different numbers (proposed b v and proposed b w imply \(v = w\));
    • acceptance of issued proposals: voted a b v implies proposed b v;
    • P2c: for every issued proposal \((b, v)\) there is a quorum \(S\) such that either (a) no acceptor of \(S\) accepted a proposal numbered less than \(b\), or (b) for some \(c < b\) an acceptor of \(S\) accepted a proposal \((c, v)\) and no acceptor of \(S\) accepted anything numbered strictly between \(c\) and \(b\); that is, \(v\) is the value of the highest-numbered proposal below \(b\) accepted by \(S\).

    Lamport states P2c for the acceptances made before the proposal is issued. Here it is required of the whole history, the form in which his algorithm maintains it: an acceptor that answered the prepare request \(b\) promised never to accept below \(b\) afterwards (Reachable states are Paxos voting histories). No timing, failure or message assumption enters this definition.

    structure Voting (Q : QuorumSystem A) (V : Type*) where
  /-- A proposal with this number and value was issued. -/
  proposed : ℕ → V → Prop
  /-- The acceptor accepted the proposal with this number and value. -/
  voted : A → ℕ → V → Prop
  /-- Different proposals have different numbers. -/
  unique : ∀ b v w, proposed b v → proposed b w → v = w
  /-- Only issued proposals are accepted. -/
  voted_proposed : ∀ a b v, voted a b v → proposed b v
  /-- Lamport's condition P2c. -/
  p2c : ∀ b v, proposed b v → ∃ S, Q.IsQuorum S ∧
    ((∀ a ∈ S, ∀ c < b, ∀ w, ¬ voted a c w) ∨
      ∃ c < b, (∃ a ∈ S, voted a c v) ∧ ∀ a ∈ S, ∀ d w, c < d → d < b → ¬ voted a d w)

    TheoremLamport's P2b#✓fully proved

    Cslib.Distributed.Paxos.Voting.p2b

    In every Paxos voting history: if the proposal numbered \(m\) with value \(v\) is chosen, then every proposal issued with a number \(n > m\) has value \(v\).

    Proof. Lamport's induction on \(n\) (Section 2.2). Let \(C\) be a quorum that accepted \((m, v)\), and let \(S\) be the quorum that P2c gives for the proposal \((n, w)\). The two quorums share an acceptor \(a\), which accepted a proposal numbered \(m < n\), so \(S\) did accept proposals below \(n\); by P2c, \(w\) is then the value of a proposal accepted by \(S\) at some number \(c < n\) with no acceptance by \(S\) strictly between \(c\) and \(n\). Since \(a\) accepted at \(m\), \(m \le c\). If \(c = m\), uniqueness of proposal numbers gives \(w = v\); if \(m < c\), the induction hypothesis applied to the proposal numbered \(c\) gives \(w = v\).

    theorem p2b {m : ℕ} {v : V} (hm : H.chosenAt m v) :
    ∀ n, m < n → ∀ w, H.proposed n w → w = v

    In every Paxos voting history, two chosen values are equal: the second safety requirement of Section 2.1, "Only a single value is chosen".

    InductiveOne step of single-decree Paxos#✓fully proved

    Cslib.Distributed.Paxos.Algorithm.Step

    The transitions of single-decree Paxos, one per action, for a quorum system:

    • prepare \(n\): the prepare request \(n\) is sent (Phase 1(a)).
    • promise \(a\), \(n\), \(r\): if the prepare request \(n\) was sent, acceptor \(a\) has responded to no prepare request numbered \(n\) or more, and \(r\) is the highest-numbered acceptance of \(a\) below \(n\), then \(a\) records \(n\) as its highest prepare number and sends the response \((a, n, r)\) (Phase 1(b)).
    • propose \(n\), \(v\), \(S\): if no proposal numbered \(n\) was issued, \(S\) is a quorum, every acceptor of \(S\) has responded to the prepare request \(n\), and \(v\) satisfies Lamport's value rule for those responses, then the proposal \((n, v)\) is issued (Phase 2(a)).
    • accept \(a\), \(n\), \(v\): if the proposal \((n, v)\) was issued and acceptor \(a\) has responded to no prepare request numbered greater than \(n\) (rule P1a), then \(a\) accepts it (Phase 2(b)).

    Messages are never removed, so any of them may be used later, repeatedly, or never. Crashes and restarts change no state: acceptors keep their state in stable storage and proposers hold none.

    inductive Step (Q : QuorumSystem A) : State A V → Action A V → State A V → Prop
  | prepare (s : State A V) (n : ℕ) :
      Step Q s (.prepare n) { s with prepares := insert n s.prepares }
  | promise (s : State A V) (a : A) (n : ℕ) (r : Option (ℕ × V)) :
      n ∈ s.prepares → (∀ k, s.maxBal a = some k → k < n) → HighestBelow s.votes a n r →
      Step Q s (.promise a n r)
        { s with maxBal := Function.update s.maxBal a (some n),
                 promises := insert (a, n, r) s.promises }
  | propose (s : State A V) (n : ℕ) (v : V) (S : Finset A) :
      (∀ w, (n, w) ∉ s.proposals) → Q.IsQuorum S → (∀ a ∈ S, ∃ r, (a, n, r) ∈ s.promises) →
      SafeValue s.promises S n v →
      Step Q s (.propose n v S) { s with proposals := insert (n, v) s.proposals }
  | accept (s : State A V) (a : A) (n : ℕ) (v : V) :
      (n, v) ∈ s.proposals → (∀ k, s.maxBal a = some k → k ≤ n) →
      Step Q s (.accept a n v) { s with votes := insert (a, n, v) s.votes }

    Related topics

    • FLP impossibility: in the same asynchronous crash-failure setting no deterministic protocol guarantees termination, which is why Paxos guarantees safety unconditionally and progress only under extra assumptions (Section 2.4).
    • Synchronous consensus with crash failures: with synchrony, consensus terminates despite crashes, at a cost of \(f + 1\) rounds.
    • Byzantine generals problem: agreement when faulty processes may lie, which Paxos's non-Byzantine model excludes.
    • Labelled transition systems: CSLib's LTS, the semantic model of the algorithm here.
    • Input/output automata: Lynch and Tuttle's model of asynchronous distributed systems, an alternative way to present such algorithms.
    • Lamport clocks: the total ordering of events that the state-machine approach needs; Paxos, run once per command (Section 3), provides one despite failures.
