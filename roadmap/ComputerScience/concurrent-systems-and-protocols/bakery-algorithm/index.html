    Bakery algorithm

    Lamport's bakery algorithm (1974) solves Dijkstra's mutual exclusion problem for \(N\) processes without any shared variable written by more than one process: each process takes a ticket one larger than every ticket it reads, and processes enter their critical sections in order of (ticket, name). These pages prove mutual exclusion, the safety part of the problem.

    Model.

    • Synchrony: none. Steps of different processes interleave arbitrarily, with no assumption on relative speeds; no fairness is assumed, since only safety is proved.
    • Shared memory: process \(i\) writes only choosing[i] and number[i] and reads the others' entries; tickets are unbounded natural numbers.
    • Atomicity: each step reads or writes one entry atomically (atomic registers), and the maximum is computed one read at a time in any order. This is weaker than Lamport's result, whose proof allows a read that overlaps a write to return an arbitrary value (safe registers, in the terminology of his later work).
    • Failures: a process may fail at any time and is reset atomically to its noncritical section with choosing[i] = number[i] = 0. Lamport also allows a period during which reads of a failed processor's memory return arbitrary values; that is not modelled.
    • Messages: none.

    The busy-waiting re-reads at L2 and L3 do not change the state and are omitted. First-come-first-served (Assertion 1) and deadlock freedom (Assertion 3) are not formalised.

    Cslib.Algorithms.Concurrency.Bakery.LocalStep

    The atomic actions of process \(p\) in the bakery algorithm, each given by its new program counter and its new values of choosing[p] and number[p]:

    • enter (L1): from the noncritical section, set choosing[p] := 1 and start reading all entries with running maximum \(0\);
    • read: read number[k] for some unread \(k\) and update the running maximum \(m\);
    • end of reads: when every entry has been read, prepare to write;
    • write: set number[p] := 1 + m;
    • exit: set choosing[p] := 0 and start the loop at index \(0\);
    • L2: at index \(j < N\), proceed to L3 when choosing[j] = 0;
    • L3: proceed to index \(j + 1\) unless number[j] ≠ 0 and \((\text{number}[j], j) < (\text{number}[p], p)\);
    • enter the critical section after index \(N - 1\);
    • leave: set number[p] := 0 and return to the noncritical section;
    • fail: at any point, return to the noncritical section with choosing[p] = number[p] = 0.

    inductive LocalStep (s : State N) (p : Fin N) : ProgramCounter N → Bool → ℕ → Prop
  | enter : s.pc p = .ncs → LocalStep s p (.doorway Finset.univ 0) true (s.number p)
  | read (U : Finset (Fin N)) (m : ℕ) (k : Fin N) : s.pc p = .doorway U m → k ∈ U →
      LocalStep s p (.doorway (U.erase k) (max m (s.number k))) (s.choosing p) (s.number p)
  | endRead (m : ℕ) : s.pc p = .doorway ∅ m → LocalStep s p (.write m) (s.choosing p) (s.number p)
  | write (m : ℕ) : s.pc p = .write m → LocalStep s p .exit (s.choosing p) (m + 1)
  | exit : s.pc p = .exit → LocalStep s p (.l2 0) false (s.number p)
  | l2 (j : ℕ) (hj : j < N) : s.pc p = .l2 j → s.choosing ⟨j, hj⟩ = false →
      LocalStep s p (.l3 j) (s.choosing p) (s.number p)
  | l3 (j : ℕ) (hj : j < N) : s.pc p = .l3 j →
      ¬ (s.number ⟨j, hj⟩ ≠ 0 ∧ Before (s.number ⟨j, hj⟩) ⟨j, hj⟩ (s.number p) p) →
      LocalStep s p (.l2 (j + 1)) (s.choosing p) (s.number p)
  | enterCS : s.pc p = .l2 N → LocalStep s p .cs (s.choosing p) (s.number p)
  | leave : s.pc p = .cs → LocalStep s p .ncs (s.choosing p) 0
  | fail : LocalStep s p .ncs false 0

    Cslib.Algorithms.Concurrency.Bakery.AheadOf

    StructureThe per-process invariant of the bakery algorithm#✓fully proved

    Cslib.Algorithms.Concurrency.Bakery.LocalInv

    The invariant of process \(i\) in a state has five parts:

    • number[i] > 0 exactly when \(i\) holds a ticket;
    • choosing[i] = 1 exactly when \(i\) is in the doorway;
    • at L2 with index \(j\): \(j \le N\) and \(i\) is ahead of every other process with name below \(j\);
    • at L3 with index \(j\): \(j < N\), \(i\) is ahead of every other process with name below \(j\), and the process named \(j\) (if different from \(i\)) is either behind \(i\) or waiting or critical;
    • in the critical section: \(i\) is ahead of every other process.

    It is the step-by-step form of the case analysis behind Lamport's Assertion 2.

    structure LocalInv (s : State N) (i : Fin N) : Prop where
  number_pos : 0 < s.number i ↔ HasTicket (s.pc i)
  choosing_eq : s.choosing i = true ↔ InDoorway (s.pc i)
  l2 : ∀ j, s.pc i = .l2 j → j ≤ N ∧ ∀ k : Fin N, k.val < j → k ≠ i → AheadOf s i k
  l3 : ∀ j, s.pc i = .l3 j → j < N ∧ (∀ k : Fin N, k.val < j → k ≠ i → AheadOf s i k) ∧
    ∀ k : Fin N, k.val = j → k ≠ i → AheadOf s i k ∨ Waiting (s.pc k)
  cs : s.pc i = .cs → ∀ k, k ≠ i → AheadOf s i k

    Cslib.Algorithms.Concurrency.Bakery.localInv_step_other

    If process \(i\) satisfies the per-process invariant and a different process \(p\) takes one atomic action, then \(i\) still satisfies it. The values of \(i\) do not change; the only work is to check that \(p\), whatever it does, stays behind \(i\) when it was behind \(i\), and that a process \(p\) that \(i\) is about to read at L3 is still either behind \(i\) or waiting.

    Cslib.Algorithms.Concurrency.Bakery.localInv_step_self

    If every process satisfies the per-process invariant and process \(i\) takes one atomic action, then \(i\) satisfies the invariant afterwards. The two informative cases are the loop statements. At L2, reading choosing[j] = 0 means that \(j\) is not in the doorway, so it is in its noncritical section (hence behind \(i\)) or holds a ticket and is no longer choosing. At L3, passing \(j\) while \(j\) holds a ticket means that \((\text{number}[j], j) \not< (\text{number}[i], i)\), hence \((\text{number}[i], i) < (\text{number}[j], j)\) since the names differ. This is the case analysis of Lamport's Assertion 2, carried out step by step.

    Cslib.Algorithms.Concurrency.Bakery.mutual_exclusion

    In every state reachable from the initial state of the bakery algorithm, if processes \(i\) and \(k\) are both in their critical sections then \(i = k\). This is condition 1 of the problem as Lamport states it ("At any time, at most one computer may be in its critical section"), which he derives from Assertion 2.

    Strength. Proved for atomic reads and writes of single entries and atomic crash-resets. Lamport's proof also covers reads that overlap a write and return arbitrary values, so his result is stronger than this one. The test module shows a reachable state with a process in its critical section, so the statement is not vacuous.
